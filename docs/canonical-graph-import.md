# Canonical graph import boundary

The web client's full export format (`frontend/apps/web/src/api/endpoints.ts`) is a project, an array of items, and directed typed links. The Rust server persists that format in `canonical_projects`, `canonical_items`, and `canonical_links`. Both SQLite and Postgres migrations use a project-scoped item key `(project_id, id)`, and links have foreign keys to both endpoints in the same project. The product intent model (`product_nodes` and `product_edges`), SWEE graph, and legacy ingest trace tables remain separate.

`POST /api/v1/import` creates a new project in one transaction. Empty or duplicate project/item IDs, duplicate links, and links whose endpoints are absent receive an error; none are silently discarded. Imports to an existing project return conflict. `/api/v1/projects` includes canonical projects alongside problem-derived legacy projects. `GET /api/v1/items` and `GET /api/v1/links` require `project_id` and return `{items|links,total}` with `limit` (1–500) and `skip` (>=0). `GET /api/v1/graph/traverse/{id}` requires `project_id`, accepts `direction=up|down|both` and `depth=0..32`, and returns graph nodes and edges from that project. `GET /api/v1/projects/{project_id}/export?format=full` returns the canonical format.

This is a valid-graph import path. A dangling import link returns HTTP 400 with `unresolved_ids`; the project is not created. `GET /api/v1/items/{id}?project_id=...` retrieves a canonical item by its scoped key for the detail route. The detail response uses the project's import timestamp because the canonical export format has no per-item timestamp.

`POST /ingest/github` has an explicit canonical opt-in: provide `project_id`, `repo` in `owner/repo` form, and `issues[]` with numeric issue numbers and absolute HTTP(S) `html_url` values. It appends stories with stable IDs `github:<owner>:<repo>:<number>` and `satisfies` links for extracted `REQ-`, `SPEC-`, `FR-`, and `NFR-` references in one transaction. The source URL, repository, and `github_issue` kind persist as optional canonical item provenance and round-trip through full export. Every referenced target must already be an item of type `requirement` in that canonical project. Missing targets return HTTP 422 with the unresolved IDs and no writes. Repeated issue IDs conflict. Bound payload requests do not use configured live GitHub credentials, and they do not write the legacy story/evidence/trace tables. Requests without `project_id` retain the existing legacy ingest behavior.

The Jira/AgilePlus ingest API still writes stories, evidence, and trace links without a canonical project binding or guaranteed target item. Unresolved or deferred targets do not appear as graph nodes until the caller imports them explicitly.

The project GraphView reads the paged canonical collections and exposes a Load more control. It adapts each link triple to a deterministic project-scoped renderer ID, and node navigation passes the project ID through both detail fetches. The browser route still requires mounted UI verification; this document does not establish that acceptance.
