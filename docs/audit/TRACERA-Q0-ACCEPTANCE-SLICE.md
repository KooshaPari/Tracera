## Decision and first execution gate

Use **Tracera itself** as the first owned product. Its checked-in endpoint contract disagrees with its handler on an exact input. This requires no second repository or invented example product. It is a genuine source/contract discrepancy; its ultimate resolution is a product decision, not an assertion that the older contract is correct.

Witness `Q0-INGEST-EMPTY`: `tests/e2e/contract/ingest-github.e2e.yml:11-15` declares `POST /ingest/github` with `{}` returns 200. `crates/tracera-server/src/handlers/ingest_api.rs:110-122` returns 422 when no live GitHub source is configured. The happy-path YAML at lines 5-10 also supplies an ignored `payload` field rather than `issues` and predicts 200. Do not silently update the oracle and declare product acceptance.

**First gate:** runtime owner may, only in a disposable, isolated process/database with all live ingestion source variables absent, submit the empty request and retain status/content-type/error-count plus process/build SHA. The expected implementation response is 422, contradicting the checked-in 200 oracle. This is a proposed execution, not a completed result. Do not POST to production/shared runtime, expose environment values, or interpret a Cloudflare response as application evidence. An unavailable runtime blocks this execution but does not erase the static discrepancy.

## Concrete semantic counterexamples to fix before trusting detectors

1. **Coverage identity mismatch:** `detectors.rs:182-190` collects capability intent IDs then searches `observation.product_id == capability_id`, although `Observation.capability_id` exists. Valid input product `tracera`, capability `ingest.github.empty-input` is wrongly treated as uncovered. Tests at `detectors.rs:340-360,399-415` set product IDs to capability IDs and leave capability_id None, so they do not guard the intended distinction.
2. **Cross-capability false contradiction:** `detectors.rs:238-245` groups by product+baseline, omitting capability. One capability passing and another failing in the same product/baseline produces a contradiction for the product mislabeled as capability (`:265-267`). Add a negative control with two distinct capability IDs and opposite results; expect no contradiction between them.
3. **Freshness attribution:** `detectors.rs:132-134` writes product ID into finding capability_id. Observation provenance is available but identity must be preserved.
4. **Coverage active-baseline filtering:** coverage logic filters kind only, not Accepted status or intent baseline (`:182-186`). Deferred/retired or historical intent must not generate current missing-proof failures without explicit policy.

These are source-demonstrable behavior counterexamples, not fresh failing-test receipts. Correct algorithms should take product-scoped accepted-baseline context and preserve product/capability/baseline independently. A finding of missing observations is UNKNOWN proof status; it is not proof a capability is absent.

## Namespace, retry and atomicity implementation contract

`Store` at `store.rs:238` exposes separate `create_story`, `create_evidence` and `create_trace_link`; no transactional batch/import operation was found in the trait. `ingest/persist.rs:38,60-106` generates `story-{external_id}` and random evidence/link IDs, then records errors after partial writes. SQLite `sqlite_store/stories.rs:52-69` uses plain INSERT. Replays can fail on story ID and skip reconciliation; this is not successful idempotency. `sqlite_store/items.rs:33-48` and `pg_store/items.rs:33-51` demonstrate underlying SQLx transactions for consistent item reads, not cross-entity write atomicity.

Q1 should add a Store-level atomic product-import operation, implemented by both DB adapters, with stable `(product_id, source_kind, source_instance, external_id)` identity and durable request-key+payload-digest receipt. Same key/same bytes returns original successful receipt; same key/different bytes returns conflict. Validate all inputs before committing; commit entities, anchors, observations, relationships and receipt together. A crash after commit before response must be safely replayable. Keep immutable observations and baseline provenance. Do not silently change partial-ingest semantics without caller review.

Tests to add (design, not run): two products same GitHub number; GitHub and Jira same external string; retry before/after restart; same-key different-payload conflict; concurrent same-key calls; injected failure at each write boundary on SQLite and PostgreSQL; old-baseline replay; project with items and zero problems remains discoverable; private anchor excluded from public projection. Existing in-memory tests `same_idempotency_key_rejects_batch`, `mixed_valid_and_invalid_batch`, and `roundtrip_ingest_then_query_by_product` in `product/ingest.rs` are unit semantics only, not these durability/transaction gates.
